# 职责匹配与现有存档的接入设计

2026-11-16（America/Phoenix） · 阶段 1 设计交付 · 阶段 3 尚未批准执行。

第一阶段的数据操作与解析器保持独立，只读注入的成员和岗位引用，不导入旧 store，不读取浏览器全局状态。独立演练的配置不修改 `platypus.v1.demo`。本设计明确后续如何接回业务，避免新匹配库成为另一份长期业务正本。

## 当前实际限制

主业务使用 `src/data/store.tsx` 的 `loadStateWithNotice`、`saveState` 和 `buildExport`，当前外层 `SCHEMA_VERSION` 为 22。`saveState` 将完整业务对象序列化到一个键；旧版读取器遇到未支持版本，会先备份再恢复示例，不能把这种恢复当作正常迁移。

`Org.id` 当前常来自演示种子。重新完成 onboarding 时仍可能沿用同一 ID，因此它不能独自证明新配置属于同一次组织工作区。人员的 `Role.holderId`、`Person.roleId` 仍服务于旧权限、交接和页面，不能为了资格池就批量改写这些字段。

## 阶段 3 的拟定存储布局

在现有业务对象中增加可选的匹配命名空间，以及单独生成并保存的本地工作区身份。匹配配置只引用现有岗位、成员、步骤和任务 ID，不复制其完整名单。

- `Org.matchingWorkspaceId`：首次显式启用新匹配时建立的稳定本地身份；新建一个组织工作区时生成新身份。它不是登录或组织权限凭据。
- `DemoState.matching`：与该身份对应的 `MatchingState`，使用自己的 `schemaVersion: 1`。
- 组织设置记录匹配模式是否启用；未设置按旧业务兼容方式运行。职责解析器不依赖 `RoleFunction`，旧 `fn` 仅保留给未迁移的显示、权限和日期等代码。
- 具体任务的分派回执留在 `MatchingState.assignments`，通过任务、工作流、步骤共同定位；实际执行人仍写进现有任务 `ownerId`。一次业务操作中同时生成任务和回执，再统一保存。

阶段 1 的仓储键 `platypus.matching.v1:<组织身份>` 仅用于隔离演练、导出及恢复验证。阶段 3 如导入这份配置，需要显式预览并检查工作区、岗位与成员引用；导入后以业务对象内的配置为正本，不对两个键持续双写。

本地仓储的 revision read/check/write 只能发现部分过期写入，不能提供跨标签页原子事务。它不作为真实多人数据库使用。跨设备及多人同时操作仍需后续服务器授权和原子修订控制。

## 外层版本迁移

根据仓库“改变业务数据结构需升级版本”的规则，阶段 3 的目标是从当时现行版本增加一个版本。以当前基线为例为 22 → 23；开工前重新核对版本，避免占用别人已经使用的编号。本阶段不实际修改版本号。

迁移分两层：

1. 外层旧业务存档迁移：保留已有组织、人员、任务、状态、提醒和历史。没有匹配配置时只增加必要的兼容字段，不推导或确认新的职责，不重分配任务，不重建整张活动图。
2. 匹配配置迁移：按 `MatchingState.schemaVersion` 独立验证。支持的配置原样接入；损坏、组织身份不符或更高版本时，保留原始配置和可恢复副本，暂停新匹配，显示原因，不删除整个组织或恢复示例。

每层迁移都应幂等。再次打开不能重复添加职责、重复创建成员关系或重复导入回执。迁移与导入前保存原始可恢复副本；保存失败时不能报告成功，也不能先删原文件或副本。

第一次启用的职责、岗位关系和成员资格必须经过用户检查。旧自由文本、模板默认职责和旧角色名不能自动被当成章程中已确认的事实。必要外部资格的缺省状态为 unknown；不根据职位名称推断已经有某个学校系统账号。

## 已有任务与新任务

| 情况 | 接入行为 |
| --- | --- |
| 已有任务，没有匹配回执 | 保留现有 owner 和状态；标明旧分派尚未关联职责，不伪造过去的人工确认 |
| 用户明确把已有任务接入新机制 | 展示职责、候选与现有执行人，确认后追加真实的新回执 |
| 新建活动或独立任务 | 按已确认要求解析；只有明确确认的分派写入实际任务；预选和备份建议不伪装为已接手 |
| 新匹配已启用但职责或候选缺失 | 留作待处理，不退回九类职能或列表第一人 |
| 改模板或改默认人 | 影响未来任务；已确认回执保持，失效的人选提示复核 |
| 旧页面手动改 owner | 新适配层须记录这次人工改派；如发现实际任务与回执不一致，暂停自动决定并提示，不覆盖实际任务 |
| 一个步骤出现在两种工作流 | 使用明确的工作流/步骤复合身份，不按标题或简单分隔符拼接串用 |

任务认领继续由业务流程处理。匹配层只决定资格和分派依据；预算步骤、日期和现有角色权限不得因为新职责标签而绕过原有检查。

## 重新设置组织 导出与恢复

重新创建工作区时显式建立新匹配身份，并提供旧配置的保留或导出途径，避免新旧任务 ID 重复时读到旧回执。普通的岗位改名和职责改名保留稳定 ID；岗位停用、成员离任和职责归档则显示具体失效原因，不重置数据。

现有完整业务导出需要包含匹配配置、修订与回执。独立匹配配置导出只代表该配置，不等于组织全量备份；导入前验证当前身份和外部引用。更高版本导出保持可下载原文，不能删未知字段后静默降低版本。

## 回滚必须保留兼容读取

不能把外层 23 的存档直接交给只认识 22 的旧读取器。阶段 3 先以单独提交加入兼容读取/恢复层，再接入功能写入；这个提交是回退基点，不能与新功能一起撤掉。

优先通过关闭新匹配模式回到旧操作入口，保留配置和已有任务。如果需要回退代码，退到保留新版本读取能力的兼容基点，或使用已验证的投影恢复工具：保留升级后的全量副本，只恢复旧业务可读投影。不得直接写低版本号欺骗读取器，不以 Reset demo、清 localStorage 或丢弃匹配数据作为回滚。

阶段 3 的必要回归：原 22 数据的语义保留、重复迁移、断电/写失败恢复、损坏子配置隔离、新版本配置不覆盖、工作区重新建立、导出再导入、模板变化不改旧任务、关闭新模式，以及兼容基点读取新版本存档。第一阶段只交付此接入设计，不宣称已执行这些旧应用集成测试。
