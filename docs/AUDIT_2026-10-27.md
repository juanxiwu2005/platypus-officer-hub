## 第 1 节 · 底层架构（给不写代码的人）

### 1.1 一句话

**我们现在没有数据库。你和干部输入的每一个字，都只存在你自己这台电脑的这个浏览器里，从来没有离开过。**

### 1.2 一张图

```
         你的电脑 / Chrome 浏览器
        ┌─────────────────────────────────┐
        │  Platypus 的全部页面            │
        │  规则引擎（算三个截止日）        │  ← 全在浏览器里跑
        │  预测（模拟 1000 次）           │     不需要联网
        │                                 │
        │  ┌─────────────────────────┐    │
        │  │ 一个叫                  │    │  ← 所有数据就是
        │  │ platypus.v1.demo        │    │     这一个"抽屉"
        │  │ 的浏览器抽屉             │    │     （一整包 JSON）
        │  └─────────────────────────┘    │
        └───────────────┬─────────────────┘
                        │ 只有问 AI 时才联网
                        ↓
            Netlify 上的 11 个小程序 /api/*
                        │  （只转发，不存数据）
```

**已验证的要点：**

- 每次你点任何东西，整包数据被重新写进那个浏览器抽屉（`src/data/store.tsx:278`）。
- 服务器上的 11 个函数**一个都不写数据**——收到问题、问 AI、送回答案、转身就忘。
- 全仓库搜 `login`、`password`、`auth`、`session`、`jwt`、`cookie`：**一处都没有。身份系统不存在。**
- 服务器上唯一的数据是 `src/data/sharedPool.ts:7` 的 **37 行硬编码常量**（4 个虚构社团的审批中位数），只读，连写入的路由都没有。

唯一的检查是"这个人存在吗"。**任何人在下拉框里选 "Alex Rivera · President"，立刻拿到全部权限。**

### 1.4 这不是失误，是你自己批准的决定

`PRODUCT_PLAN.md` §16 决定第 3 条（你 10/22 批准）：

> **3. 数据：** v1.0 只存在浏览器（虚构演示社团），v1.5 再上服务器存储和登录。建议：批准。

理由写在计划里，而且理由是对的：**"Phase 3 不在服务器存任何参与者数据，IRB 最简单"。**

代码里甚至有一道硬锁保证你**物理上无法录入真实学生信息**：`src/data/settings.ts:41-43` 强制邮箱必须 `@example.org`、电话必须 `555-01xx`，否则保存失败。

## 第 2 节 · 数据治理：你说的"最底层"现在是 0%

你说"所有 data 都应该有记录、有时间戳，从而提供更好的反馈和改进"。逐字段核对 `src/data/types.ts` 的结果：

| | 情况 |
|---|---|
| 有时间戳的实体 | 约 8 个，而且**只有"天"级精度**（`2026-10-22`，没有时分秒） |
| 记录了"谁改的" | **只有 2 个**（延期申请 `types.ts:209-221`、提醒 `types.ts:191-199`） |
| 完全没有时间戳 | `ChangeSet`（AI 改动记录本身！）、`Event`、`Funding`、`Contact`、`Role`、`Goal`、看板设置 |
| 人在界面上直接改的操作 | **100% 无审计**。改负责人、改截止日、拖看板、改预算、改设置——全是原地覆盖，旧值和操作者都丢（`store.tsx:75-102` 的 `updateNode` 只把 `lastUpdate` 覆盖成当天） |
| 时间戳的来源 | **不是真实时钟**，是固定在 `2026-10-22` 的模拟时钟。全仓库 `new Date()` 只出现在生成 ID 的地方 |
| 你（研究者）能看到用户做了什么吗 | **完全不能。** 服务器端唯一的日志是报错时 `console.error(e)`（`netlify/lib/http.mts:28`）。没有请求日志、没有埋点、没有 token 用量记账 |
| 用户点"这不对"的反馈去哪了 | 写进**用户自己的浏览器**（`store.tsx:107`），然后被 "Reset demo" 按钮删掉 |
| 只追加的日志 | 有 4 个（沉默协议、AI 改动、通知、贡献），但**人的直接操作一条都不记** |

**所以：这个底层能力目前是 0%，不是 30%。** 因为"可审计"的前提是有一个只追加、服务器写入、单调时间的事件表，而这要求先有数据库和身份。

### 好消息：切口已经现成了

你的 **40 种操作全部经过同一个入口**——`src/data/store.tsx:104-245` 一个 switch 语句。把它改成「每个动作先落一行事件日志，再执行」，是一次性改造，之后"谁在什么时候改了什么"就是免费的。

**这是整个代码库最大的结构性机会，而且它正好对应你论文里"data governance 作为最底层"这个主张。**

## 第 3 节 · 三件本周就该知道的事

### 🔴 3.1 改一次数据结构 = 所有用户数据无声清零

```js
// src/data/store.tsx:247-258
if (parsed && parsed.schemaVersion === SCHEMA_VERSION) return parsed
...
return seedDemo()   // 版本号不一样 → 直接恢复演示数据
```

版本号不等就**直接重置**。没有迁移、没有备份、没有提示、**连导出按钮都没有**。而这个版本号**已经被改过 3 次**（3 → 4 → 5），每次注释都写着"旧版浏览器数据恢复种子"。

**意思是：每次开发者改数据结构并推送上线，所有真实用户输入的全部内容会在下次打开网页时无声消失。**

同一个 `catch` 还把 JSON 解析失败也吞掉（`store.tsx:254-256`），任何数据损坏 = 静默恢复种子。

而且保存失败也是静默的（`store.tsx:260-266`）：浏览器抽屉塞满（配额通常 5 MB，而单个附件可占 70 万字符、日志只增不减）之后，界面**不会有任何提示**，用户继续操作，关掉标签页就全丢。

**最便宜的保险（改 5 行）：** 版本不匹配时把旧数据另存一份，并加一个"导出我的数据为 JSON"按钮。这对现在的 Phase 3 参与者立刻有用。

### 🔴 3.2 一个两难：关掉保护，AI key 就暴露

主审从外部实测（2026-10-27）：

```
GET  https://platypus-officer-hub.netlify.app/     → 401
POST .../api/chat        → 401
POST .../api/command     → 401
POST .../api/ask         → 401
POST .../api/parse-brief → 401
POST .../api/pool        → 401
```

整个站点还挂着 Netlify 访问保护，**只有登录你 Netlify 账号的人能打开**。README 里写的 "Live site" 目前对任何人都打不开。

这造成一个必须一起解决的两难：

- **关掉保护** → Phase 3 参与者能用了，但你的付费 AI key 变成公网上一个**无鉴权、无限流、无配额、无用量记录**的 LLM 代理，单请求可塞 **400 KB**（`netlify/functions/chat.mts:29`）。一个 `while true; curl ...` 循环在 DeepSeek 上是几百到几千美元；按你文档建议切到 OpenAI 或 Anthropic 就是**每小时数百美元**，而且你**事后也查不到发生过什么**。
- **不关保护** → Phase 3 参与者打不开网站。

**现在唯一保护你 API key 的东西，就是那个让 Phase 3 无法进行的访问保护。**

最小动作（几小时）：
1. `chat.mts:29` 的 body 上限从 400 KB 降到 40 KB（一行）
2. 加 Netlify 自带的限流，或一个共享 secret header
3. **删掉 4 个没人调用但会烧同一把 key 的端点**：`/api/pool`（完全死代码）、`/api/parse-brief`、`/api/plan/draft`、`/api/replies/classify`（只被废弃的 `/legacy/` 调用）
4. 删掉 `/legacy/`——它已经半坏了，还在调 6 个**根本不存在**的端点

### 🔴 3.3 一个藏得很深的定时炸弹：2027-05-08

ASU 学年日历**写死**在 `src/engine/calendar.ts:15-60`，只有 2026 和 2027 两年，学期表到 `2027-05-08` 结束。

日历用完之后，代码把**每一天**都判定为"学期之间的假期"（`calendar.ts:80-86`），于是倒推日期时一路往前跳。审计员独立复算验证：

```
2027-10-15 的活动，往前倒 14 个"学生工作日"
→ 算出 2027-04-13      （提前了整整 6 个月，循环跑了 185 天）
正确答案应该是 2027-09-27
```

**而且不报任何错**——`schedule.ts:290-324` 的警告清单里没有"超出已知日历"这一项。从 2027 年秋季学期第一个活动开始，引擎会给出提前半年的日期，界面上看起来完全正常。

另外，**这个 app 现在认为今天是 2026-10-22**（真实日期 10/27）。全仓库**没有任何一处**把真实时钟接进 `state.today`，只有社长手动点 "+1 天 / +3 天 / +10 天"。所有"逾期"判断、沉默协议计时、预测、链接过期，全锚在这个假日期上，而且会越偏越多。

短期修法：补 2027–2028 的日历（半小时）。正确修法：超出已知范围时抛一个**红色警告**——让它坏得明显，而不是坏得安静。

## 第 6 节 · "创建不了任务"——两名审计员独立查到同一根因

### 6.1 根因：不是权限问题，是入口不存在


**你的体验是**：打开 Tasks → 看到一个表格 → 找不到任何"新建"按钮 → 顶栏、右栏、页面里都没有 → 合理推断"我没权限"。

**讽刺的是：`addBoardTask`（`board.ts:60-71`）根本不检查权限，任何角色都能创建任务。** 功能一直是开放的，只是入口藏在一个需要先切视图、再滚到列底部的位置。

**这是 affordance（可见的操作可能性）缺失，不是权限限制。** 而它的上游原因是第 2 阶段没有画用户流程图——没人画过"创建任务"这条流，所以入口漏了。

### 6.2 第二条路（问 AI）对非社长是死路

`add_node` **不在**可立即生效的小改动白名单里（`commands.ts:24` 的 `SMALL_OPS` 只有 5 个），所以必须走审批卡，而审批卡对非社长**整体禁用**：

```js

<button disabled={!canNudge}>Apply this change</button>
{!canNudge && <span>The president or VP approves changes.</span>}
```

**5 个演示干部里只有 Alex（社长）能走通这条路。**

而你很可能当时就不是社长——`src/pages/Join.tsx:10` 默认预选的是**非社长**，保存后 `:20` 直接把查看者切成那个人。一切成非社长，Setup、看板 Customize、Demo clock、发提醒、**以及所有任务字段编辑**会同时消失。

### 6.3 就算你是社长，还有三个坎

1. **独立任务必须先手填一个日期**：`changeReview.ts:18` 要求有效日期，而默认值来自 `humanEventDate()`（`commands.ts:162-170`），它只认句子里显式写出的日期。"add a task: 订名牌" → 空 → 点 Apply 直接报错。
2. **本地语法只认一种写法**：`commands.ts:143` 的正则是 `^(?:add|create) (?:a )?(?:task|node|step)`。所以 `create a new task...`（"new" 挡住了）和 `I want to create a task...`（必须以 add/create 开头）**都不匹配**。
3. **AI 猜错一个 ID，整条改动被丢弃**，回你一句 "I couldn't turn that into a change I'm allowed to make."（`chatCards.ts:77`）——读起来也像权限问题。

### 6.4 还有一个没人发现的 bug

`board.ts:64-67`：**非社长在 "Not claimed" 列点"+ Add task"，卡片会出现在 "To do" 列**，没有任何说明。

更糟：**在 "Done" 列新建，状态直接是 `done` 且 `completedOn = today`（`board.ts:69`）** —— 任何干部可以凭空造一个"已完成"任务，而 `canMoveTask`（`board.ts:22`）却规定"重开已完成任务要问社长"。**审批模型被创建路径绕过了。** 这条路径没有任何测试覆盖。

## 第 9 节 · 做得好的部分（不要动）

这部分是真话，不是安慰。两名审计员独立给出了同样的评价。

1. **AI 供应商适配器**（`netlify/lib/ai.mts`）—— 换 DeepSeek / ASU AIR / OpenAI / Anthropic 只改环境变量，零代码改动。审计员评价："教科书级，比大多数生产代码好。"
2. **AI 的权限笼子** —— 这是**项目最值钱的东西，也是论文最该写的部分**：
   - AI 只能用 17 种白名单操作，所有未知字段（含任何日期）**直接消失**（`commands.ts:51-123`）
   - AI 写的日期，只有和数据里已有日期完全一致的才保留，其余替换成 `[date in plan]`（`chatCards.ts:20-43`）
   - **规则问答正文不是 AI 写的**：AI 只能选规则编号，正文由服务器用真实规则原文重建（`ruleAnswers.ts:5-11`）
   - **岗位手册同理**：AI 只能选来源 ID，正文一律用原始记录（`handbook.ts:11-19`）
   - 提醒只让 AI 写一句 ≤10 词，且禁用一串措辞
   - 改动全部无效时会**明确告诉用户**"我做不到"，不假装成功（`chatCards.ts:77`）
   - 测试里真的喂了恶意输入（伪造 `delete_node`、假 ownerId、`latestStart: "2099-01-01"`、注入假规则 R99）并断言被拦掉
3. **规则引擎算法** —— 倒推 → 顺推 → 红黄警告，纯函数、确定性、环检测用标准 Kahn 算法、每个日期带一句"为什么"。`engine.test.ts:54-90` 对示例活动的**全部 20 个步骤逐一断言三个日期**。
4. **发给 AI 的数据有真实的脱敏**：排除别人的私人缓冲、私信、附件、密钥，服务器再按正则过滤一遍，还限深度/长度。测试真的断言了密钥不外泄。
5. **测试套件** —— 不是摆设。`e2e/tasks.spec.ts:118-143` 用真鼠标拖拽测看板并直接断言 localStorage 内容。
6. **诚实标注 AI 来源** —— "Local fallback · server unavailable"、`AI_TESTS.md` 明确拒绝把模拟结果当真实验收。**原型里很罕见，别丢。**
7. **没有任何密钥被提交进仓库。** 全历史扫过，干净。
8. **预测把假设摊开给用户看**（`forecast.ts:6-12` 的 `FORECAST_ASSUMPTIONS`，含"这不是官方周转数据"的声明）。
9. **第 1 阶段（定位与用户研究）** —— 整个项目最扎实的一环。

### 明确不要现在优化的

- **`forecast.ts` 的 1000 次迭代** —— 当前规模下不是问题（有记忆化 + 性能断言）。等节点数过 150 再说。现在优化是浪费时间。
- **UI 层的权限检查** —— 上了数据库之后它会变成"数据库强制 + UI 友好提示"的双层结构，现在这一层不是白写的。
- **三栏布局 / 字数纪律的大方向** —— 它针对的是真问题（干部不会用复杂工具），只是执行方式有偏差。

## 第 10 节 · 1000 个社团会先撞到哪面墙

按顺序：

1. **第 0 天就撞墙** —— 没有数据库 = 没有社团。两个干部看不到同一份数据，手机打不开电脑生成的链接。**产品的核心承诺（团队协同）在架构上不成立，不是性能问题，是逻辑上不可能。**
2. **第一次部署** —— `SCHEMA_VERSION` 一改，1000 个社团数据同时清零。
3. **第一天的 AI 账单** —— 无鉴权无限流。
4. **浏览器抽屉塞满** —— 静默丢数据不提示。
5. **卡顿** —— 一个社团一学期 12 场活动 ≈ 280 个节点，一次点击要算 3–6 次完整排程 + 预测。
6. **运营上你什么都看不见。**

### 但要换的只有两层

**存储 + 身份。** 规则引擎（约 980 行）、流程模板、AI 白名单校验、AI 适配器**全是纯函数、有测试、可以原样搬过去**。

**这是一次重写数据层，不是重写产品。**

而且数据模型本身是**为多租户设计过的**：`types.ts:8-16` 的 `RoleFunction` 是规范化枚举，注释明确写"Every club role maps to one, so playbooks and cross-club data line up"。`Node` 有完整的 RACI、依赖、四种锚点。**搬进 Postgres 基本是一比一的事。这是项目除了 AI 笼子之外第二值钱的资产。**

按你计划里已经写好的 **Supabase（Postgres + 行级隔离 + 邮箱一次性链接登录）** 是对的选择。它一次解决四件事：持久化、多人共享、`org_id` 租户隔离**在数据库层强制**（这样权限判断就从"前端可改的开关"变成"数据库拒绝写入"）、以及学生场景最合适的 magic-link 登录。

**要说清楚的代价：**
- 🔴 **一旦服务器留存真实学生数据，IRB 范围就变了**，必须先在 Marcie 那边走修改。**这是日程上的硬依赖，排在所有技术工作之前。**
- 供应商锁定（RLS 策略不好搬，但底下是标准 Postgres，数据能带走）
- 免费层项目不活跃会暂停，真实试用前要升付费
- 需要新增一套"离线/失败"处理——现在那种 `try/catch` 吞掉错误的写法，联网后会变成**静默数据丢失**
