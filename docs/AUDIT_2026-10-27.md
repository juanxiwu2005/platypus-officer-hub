## Section 1 · Underlying architecture (for people who do not code)

### 1.1 In one sentence

**We currently have no database. Every word you and the officers enter exists only in this browser on your own computer and has never left it.**

### 1.2 A diagram

```
             Your computer / Chrome browser
        +-----------------------------------------+
        | All Platypus pages                      |
        | Rule engine (computes three deadlines)  | <- All run in the browser
        | Forecast (1,000 simulations)            |    No network required
        |                                         |
        |  +---------------------------------+    |
        |  | A browser storage drawer named  |    | <- All data is in
        |  | platypus.v1.demo                |    |    this one "drawer"
        |  |                                 |    |    (one JSON bundle)
        |  +---------------------------------+    |
        +-------------------+---------------------+
                            | Network used only when asking AI
                            v
              11 small Netlify functions /api/*
                            | (forward requests; store no data)
                            v
                     DeepSeek (AI provider)
```

**Verified points:**

- Every time you click anything, the entire data bundle is rewritten to that browser storage drawer (`src/data/store.tsx:278`).
- **None of the 11 server functions writes data**: each receives a question, asks AI, returns the answer, and immediately forgets it.
- A repository-wide search for `login`, `password`, `auth`, `session`, `jwt`, and `cookie` finds **zero occurrences. There is no identity system.**
- The only server-side data is **37 lines of hardcoded constants** in `src/data/sharedPool.ts:7` (approval medians for 4 fictional student organizations). It is read-only; there is not even a write route.

### 1.3 What "multiple officers collaborating" actually means

The **"View as"** dropdown at the top right is a dress-up game, not a login:

```js
// src/data/store.tsx:148
case "setViewer":
  return state.people.some(p => p.id === action.viewerId) ? {...} : state
```

The only check is “Does this person exist?” **Anyone who selects "Alex Rivera · President" in the dropdown immediately gets full permissions.**

| What you might think | What actually happens |
|---|---|
| Maya received a notification | A row containing `recipientId: maya` is added to the same JSON bundle. The code comment itself says "nothing is sent externally" (`taskWorkflow.ts:21`) |
| An officer received a link on their phone | The link works only in **the browser that generated it**. Opening it on the officer's phone shows "This link is expired, changed, or unavailable in this browser." (`Officer.tsx:23`) |
| Two officers enter data separately | They have two **completely independent copies that never merge**. There is no server, so there is nowhere to merge them |
| Someone else's "private" information | Other people's private buffers, direct messages, and attachments are **all in the same JSON bundle**. "Private" means only that rendering filters them out; switching View as or opening developer tools reveals them |

### 1.4 This was a decision you approved yourself, not an oversight

`PRODUCT_PLAN.md` §16, decision 3 (approved by you on 10/22):

> **3. Data:** v1.0 stores data only in the browser (a fictional demo student organization); server storage and login come in v1.5. Recommendation: approve.

The code even has a hard lock to ensure that you **cannot actually enter real student information**: `src/data/settings.ts:41-43` requires email addresses to end in `@example.org` and phone numbers to match `555-01xx`; otherwise, saving fails.

**For a thesis prototype that needs IRB approval, this is the right engineering decision.** You do not need to blame yourself for "not having a database."

## Section 2 · Data governance: the “foundation” you described is currently at 0%

You said, "All data should be recorded and timestamped to provide better feedback and improvements." Here are the results of checking `src/data/types.ts` field by field:

| | Status |
|---|---|
| Entities with timestamps | About 8, with **day-level precision only** (`2026-10-22`, without hours, minutes, or seconds) |
| Records of "who changed it" | **Only 2** (extension requests, `types.ts:209-221`; reminders, `types.ts:191-199`) |
| No timestamps at all | `ChangeSet` (the AI change record itself!), `Event`, `Funding`, `Contact`, `Role`, `Goal`, and board settings |
| Changes people make directly in the interface | **100% unaudited.** Changing owners, changing deadlines, dragging board cards, changing budgets, changing settings: all overwrite values in place, losing both the old value and the actor (`updateNode` in `store.tsx:75-102` merely overwrites `lastUpdate` with the current day) |
| Timestamp source | **Not a real clock**, but a simulated clock fixed at `2026-10-22`. Throughout the repository, `new Date()` appears only in ID generation |
| Can you (the researcher) see what users did? | **Not at all.** The only server log is `console.error(e)` on errors (`netlify/lib/http.mts:28`). No request logs, instrumentation, or token-usage accounting |
| Where does feedback go when users click "That's wrong"? | Into **the user's own browser** (`store.tsx:107`), then deleted by the "Reset demo" button |
| Append-only logs | There are 4 (silence protocol, AI changes, notifications, contributions), but **none record any direct human action** |

**So this underlying capability is currently at 0%, not 30%.** Auditability requires an append-only, server-written event table with monotonically increasing timestamps, which first requires a database and identity.

### Good news: the integration point already exists

All **40 action types pass through the same entry point**: one switch statement in `src/data/store.tsx:104-245`. Changing it so that "each action first appends an event-log entry, then executes" is a one-time change that subsequently gives you "who changed what, and when" automatically.

**This is the largest structural opportunity in the entire codebase, and it directly matches your thesis's argument that "data governance is the foundation."**

## Section 3 · Three things you need to know this week

### 🔴 3.1 One data structure change = all user data silently reset

```js
// src/data/store.tsx:247-258
if (parsed && parsed.schemaVersion === SCHEMA_VERSION) return parsed
...
return seedDemo()   // Different version number → immediately restore demo data
```

A version mismatch **immediately resets the data**. There is no migration, backup, or warning, **not even an export button**. This version number **has already been changed 3 times** (3 → 4 → 5), each time with a comment saying "reset older browser data to seed data."

**This means that every time a developer changes the data structure and deploys it, everything real users have entered silently disappears the next time they open the site.**

The same `catch` also swallows JSON parsing failures (`store.tsx:254-256`): any data corruption = a silent reset to seed data.

Save failures are silent too (`store.tsx:260-266`): once browser storage fills up (the quota is typically 5 MB, while one attachment can occupy 700,000 characters and logs only grow), the interface **shows no warning at all**. Users keep working, then lose everything when they close the tab.

**The cheapest safeguard (5 lines changed):** save a separate copy of old data when versions do not match, and add an "Export my data as JSON" button. This immediately helps current Phase 3 participants.

### 🔴 3.2 A dilemma: disabling protection exposes the AI key

External checks performed by the lead auditor (2026-10-27):

```
GET  https://platypus-officer-hub.netlify.app/     → 401
POST .../api/chat        → 401
POST .../api/command     → 401
POST .../api/ask         → 401
POST .../api/parse-brief → 401
POST .../api/pool        → 401
```

The entire site still has Netlify access protection enabled: **only someone signed into your Netlify account can open it**. The "Live site" in the README is currently inaccessible to everyone else.

This creates a dilemma whose two sides must be addressed together:

- **Disable protection** → Phase 3 participants can use the site, but your paid AI key becomes a public LLM proxy with **no authentication, rate limits, quotas, or usage records**, accepting **400 KB** per request (`netlify/functions/chat.mts:29`). A `while true; curl ...` loop costs hundreds to thousands of dollars on DeepSeek; switching to OpenAI or Anthropic as your documentation suggests means **hundreds of dollars per hour**, and you **cannot investigate what happened afterward**.
- **Keep protection enabled** → Phase 3 participants cannot open the site.

**The only thing currently protecting your API key is the same access protection that prevents Phase 3 from proceeding.**

Minimum action (a few hours):
1. Reduce the body limit at `chat.mts:29` from 400 KB to 40 KB (one line).
2. Add Netlify's built-in rate limiting or a shared secret header.
3. **Delete 4 unused endpoints that can still incur charges against the same key**: `/api/pool` (entirely dead code), `/api/parse-brief`, `/api/plan/draft`, and `/api/replies/classify` (called only by the abandoned `/legacy/`).
4. Delete `/legacy/`: it is already partly broken and still calls 6 endpoints that **do not exist at all**.

### 🔴 3.3 A deeply hidden time bomb: 2027-05-08

The ASU academic calendar is **hardcoded** in `src/engine/calendar.ts:15-60`, covering only 2026 and 2027; its semester table ends on `2027-05-08`.

After the calendar runs out, the code classifies **every day** as an “intersemester break” (`calendar.ts:80-86`), so backward date calculations keep skipping further back. An auditor independently recalculated and verified:

```
For an event on 2027-10-15, count backward 14 "student business days"
→ Calculates 2027-04-13      (a full 6 months too early; the loop traversed 185 days)
The correct answer should be 2027-09-27
```

**No error is reported, either**: the warning list in `schedule.ts:290-324` has no "outside the known calendar" entry. Starting with the first event of the fall 2027 semester, the engine will produce dates six months too early while the interface looks completely normal.

Also, **the app currently thinks today is 2026-10-22** (the actual date is 10/27). **Nowhere in the repository** is the real clock connected to `state.today`; the president can only click "+1 day / +3 days / +10 days" manually. Every overdue check, silence-protocol timer, forecast, and link expiry is anchored to this simulated date, and the discrepancy will keep growing.

Short-term fix: add the 2027–2028 calendars (half an hour). Proper fix: display a **red warning** when a date is outside the known range, making failures visible rather than silent.

## Section 6 · “Cannot create a task”—two auditors independently found the same root cause

### 6.1 Root cause: the entry point is missing; permissions are not the problem

```js
src/pages/Tasks.tsx:20   const [view, setView] = useState<View>("table")   // The default view is Table
src/pages/Tasks.tsx:33   Table view → TaskTable (:41-72)   ← No "+ New" anywhere in the table
src/pages/Tasks.tsx:35   Timeline view → TaskTimeline (:132-138)  ← None here either
src/pages/Tasks.tsx:125  <button className="board-add-btn">+ Add task</button>
                         ↑ The only entry point, at the very bottom of each Board column
```

**Your experience is**: open Tasks → see a table → find no "New" button → none in the top bar, right rail, or page → reasonably conclude, "I don't have permission."

**Ironically, `addBoardTask` (`board.ts:60-71`) does not check permissions at all: any role can create tasks.** The feature has always been available, but its entry point is hidden where you must first switch views and then scroll to the bottom of a column.

**This is a missing affordance (a visible indication of an available action), not a permission restriction.** The upstream cause is that no user-flow diagram was drawn in stage 2: nobody mapped the "create task" flow, so its entry point was omitted.

### 6.2 The second path (Ask AI) is a dead end for anyone other than the president

`add_node` is **not** on the allowlist of small changes that take effect immediately (`SMALL_OPS` at `commands.ts:24` contains only 5 operations), so it must use an approval card, and the approval card is **entirely disabled** for anyone other than the president:

```js
// src/components/rail/ChangeCard.tsx:111-113
<button disabled={!canNudge}>Apply this change</button>
{!canNudge && <span>The president or VP approves changes.</span>}
```

**Of the 5 demo officers, only Alex (the president) can complete this flow.**

You were probably already viewing as someone other than the president: `src/pages/Join.tsx:10` preselects a **non-president** by default, and after saving, `:20` immediately switches the viewer to that person. Once you switch to a non-president, Setup, board Customize, Demo clock, sending reminders, **and editing every task field** all disappear at once.

### 6.3 Even the president faces three more hurdles

1. **A standalone task first requires a manually entered date**: `changeReview.ts:18` requires a valid date, but the default comes from `humanEventDate()` (`commands.ts:162-170`), which recognizes only dates explicitly written in the sentence. "add a task: \u8ba2\u540d\u724c" (Chinese task text: order name badges) → empty → clicking Apply immediately produces an error.
2. **The local parser recognizes only one phrasing**: the regex at `commands.ts:143` is `^(?:add|create) (?:a )?(?:task|node|step)`. Both `create a new task...` (blocked by "new") and `I want to create a task...` (must start with add/create) **fail to match**.
3. **If AI guesses one ID incorrectly, the entire change is discarded**, with the reply "I couldn't turn that into a change I'm allowed to make." (`chatCards.ts:77`), which also sounds like a permission problem.

### 6.4 Another bug nobody noticed

`board.ts:64-67`: **when a non-president clicks "+ Add task" in the "Not claimed" column, the card appears in "To do"**, with no explanation.

Worse: **creating a task in the "Done" column immediately gives it status `done` and `completedOn = today` (`board.ts:69`)**. Any officer can invent a "completed" task, while `canMoveTask` (`board.ts:22`) requires the president's approval to reopen a completed task. **The creation path bypasses the approval model.** No tests cover this path.

## Section 10 · The first wall 1000 clubs will hit

In order:

1. **A dead end on day 0**—no database = no student organization. Two officers cannot see the same data; a phone cannot open a link generated on a computer. **The product's core promise (team collaboration) is architecturally impossible. This is a logical impossibility, not a performance issue.**
2. **First deployment**—change `SCHEMA_VERSION`, and 1000 student organizations' data is wiped at once.
3. **First day's AI bill**—no authentication or rate limiting.
4. **Browser storage fills up**—data is silently lost without a warning.
5. **Lag**—12 events per student organization per semester ≈ 280 nodes; one click computes the full schedule + forecast 3–6 times.
6. **You have no operational visibility.**

### But only two layers need replacing

**Storage + identity.** The rule engine (about 980 lines), workflow templates, AI allowlist validation, and AI adapter **are all pure functions, have tests, and can be moved over unchanged**.

**This is a rewrite of the data layer, not the product.**

The data model itself was also **designed for multiple tenants**: `RoleFunction` in `types.ts:8-16` is a normalized enum, with the explicit comment "Every club role maps to one, so playbooks and cross-club data line up". `Node` has complete RACI, dependencies, and four anchor types. **Moving it into Postgres would be almost one-to-one. This is the project's second most valuable asset after the AI cage.**

The **Supabase (Postgres + row-level isolation + email magic-link login)** already specified in your plan is the right choice. It solves four things at once: persistence, sharing among multiple users, `org_id` tenant isolation **enforced at the database layer** (turning permission checks from "a frontend switch that can be changed" into "the database rejects the write"), and magic-link login, which best fits students.

**Costs that must be made explicit:**
- 🔴 **Once the server retains real student data, the IRB scope changes**; an amendment must go through Marcie first. **This is a hard scheduling dependency that comes before all technical work.**
- Vendor lock-in (RLS policies are difficult to move, but the underlying database is standard Postgres, so the data is portable)
- Inactive free-tier projects are paused; upgrade to a paid tier before a real trial
- A new set of offline/failure handling is needed—the current `try/catch` pattern that swallows errors would become **silent data loss** once networked
